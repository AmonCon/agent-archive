# 上游代码怎么读：要不要下载

每次要跟 MAGPIE / cc-switch 这种一天几十个提交的项目，第一个问题都是
「是不是得把仓库拉下来」。答案是：**不用**。GitHub 上能看，而且有几种比
「下载整个仓库」便宜得多的读法。这篇把我们实测过的几条路径和代价记下来，
下次直接选，不用再试。

数据是 2026-11-03 在这台机器上量的（magpie `ace8ee1e → a3768cdd`、
cc-switch `9941a645 → 7afceec1`，都是 3 天量）。

## TL;DR

| 你想做的事 | 用什么 | 代价 |
|---|---|---|
| 看某个文件的现在长什么样 | `raw.githubusercontent.com/<owner>/<repo>/main/<path>` | 一个请求，~1 秒，93 KB |
| 看某个文件、要行号和语法高亮 | `github.com/<owner>/<repo>/blob/main/<path>` | 一个请求，~500 KB HTML |
| 看「这三天改了什么」 | `github.com/<owner>/<repo>/compare/<旧sha>...main.diff` | 一个请求拿全量 diff：cc-switch 1.2 MB / 8 秒，magpie 13.6 MB / ~30 秒 |
| 翻提交标题、找线索 | `api.github.com/repos/<owner>/<repo>/commits?per_page=50` | 60 次/小时（未认证），一次翻 50 条 |
| **每天跟踪、要 diff、要跨文件 grep** | **本地 sparse 浅镜像** | **首次 ~10 MB，之后每次只取增量** |

## 为什么最后还是选了本地镜像

因为在「每天跟踪」这件事上，GitHub 的那几种看法各有硬伤：

- **单文件 raw / blob**：一次只能看一个文件，没有「这三天变了哪些」这个视角。
  我们每轮要看的是变化，不是现状。
- **compare.diff**：能一次拿到全量 diff，实测可用（magpie 13.6 MB 也没被拒），
  但每天重新拉一遍 13 MB，而且拿到的是一大坨文本——没有 git 的按路径过滤、
  没有 `git log` 把提交和文件对上、不能在本地对全部文件 grep。
- **API**：未认证 60 次/小时，翻提交列表可以，翻代码不行（code search 要认证，
  实测 401）。
- **网页 blob**：单个文件 500 KB HTML，读十几个文件就是几 MB 的无用标签。

本地镜像换来的能力是 git 本来就擅长的事：`diff --name-status` 按关注目录过滤、
`log --name-only` 把提交和文件归并、`show <sha>:<path>` 按版本读、`grep` 全库搜。
这些是「从 diff 里挑出值得读的那 5%」的前提，光看网页做不到。

## 镜像到底占多少：实测五种取法

同一台机器、冷缓存、同一个仓库（magpie，工作树 6830 个文件）：

| 取法 | 耗时 | 落盘 | 说明 |
|---|---|---|---|
| 完整 clone | 139 s | 358.6 MB | 含全部历史 |
| `--depth=1 --filter=blob:none` | 60 s | 209.9 MB | 省的是历史，工作树仍然全部落盘 |
| `--depth=1 --filter=blob:none --sparse`，再只勾三个目录 | **11.5 s** | **1.3 MB → 10.3 MB** | 只取 `internal/sessions`、`internal/library`、`docs/subsystems` |
| 我们现在用的 `--depth=200 --filter=blob:none` | — | 219.3 MB | 要跟 diff 就得有旧端，所以留了浅历史 |
| cc-switch `--depth=1 --filter=blob:none` | 30 s | 100.5 MB | 同 magpie |

**结论**：真正的浪费不是「下载」，是「把用不到的子目录也 checkout 出来」。
magpie 的 `internal/gui` 一家就 1298 个文件、3.6 万行改动，我们从不需要读它。
如果只想看会话相关的那几百个文件，sparse 能把 210 MB 压到 10 MB，快 5 倍。

> 注意：sparse 镜像里 `git show <sha>:<path>` 依然可用（缺的 blob 会按需取），
> 所以「只落盘三个目录」不影响按版本读文件，也不影响对这几个目录做 diff。

## 每天跟新的推荐流程

```sh
node research/upstream/refresh.mjs            # 只看有没有新提交（秒级）
node research/upstream/refresh.mjs --diff     # 拉增量，列出关注范围内的改动文件
node research/upstream/triage.mjs             # 把改动排成「先读哪」的清单
```

`triage.mjs` 是按阅读价值排的：核心逻辑（session/parse/transcript/cache/index）
加分，UI/网关/预设表/计费减分，新增文件单独列出（新子系统通常藏在那里）。
它只负责排序，判断仍然要人做，结论写进 `LESSONS.md`。

## 三个已经踩过的坑

1. **`git fetch` 之后本地 `HEAD` 不会动。** 新提交在 `FETCH_HEAD` 里。
   读新版要用 `git show FETCH_HEAD:<path>`，不是直接读工作树文件（工作树还是旧 pin）。
2. **浅克隆里「有提交对象」不等于「能走通」。** 对象在本地，但 graft 把历史截断了，
   `git diff pin..FETCH_HEAD` 会报 `bad revision`。要按 depth 逐级加深，不能只
   `fetch --depth=1 <sha>`。`refresh.mjs` 已经修了这个（会 200 → 800 → 3000 → 12000
   逐级加深，最后才 unshallow）。
3. **`compare/<a>...<b>.diff` 的 URL 里是三个点**，不是两个。两个点是
   `a..b`（可达范围），三个点是 merge-base 对比；GitHub 两种都支持，但拿到的
   内容不同。

## 什么时候才值得真下载

- 要改上游代码、提 PR：完整 fork + clone。
- 要在本地跑它的测试复现问题：`--depth=1` 就够（历史没用）。
- 只是读、只是跟：sparse 浅镜像 + `git show`，或者干脆只看 raw / compare.diff。

我们属于第三种，所以仓库里**不存上游源码**（`reference-src/` 里那几份是
2026-10-21 的早期节选，已经过时），只存「读到哪一版」和「学到了什么」。
