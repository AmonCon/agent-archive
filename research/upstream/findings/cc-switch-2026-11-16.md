## §2 WorkBuddy 用量 / 额度

### 2.1 `session_usage_workbuddy.rs` 的数据源与格式

- 数据源：`<data dir>/projects/<cwd>/<sessionId>.jsonl` 顶层会话文件 + `<sessionId>/subagents/*.jsonl`；子代理文件里的请求算父会话的（`session_usage_workbuddy.rs:1-12,41-72`；文件枚举复用 `session_manager/providers/workbuddy.rs:68-102` 的 `usage_files()`）。
- 格式：一次模型请求的 `providerData.rawUsage` 记在该请求的**最后一个事件**上——可能是一条 assistant `message`，也可能是一条 `function_call`（工具调用往往承载大部分 token）（`workbuddy.rs:1-13,257-301`）。
- 请求 id：`workbuddy:{session_id}:{record.id}`；`record.id` 是事件 id，发生文件重写时靠 `session_usage_dedup` 的永久回执挡住重复（`session_usage_workbuddy.rs:88-97,153-161`）。
- 只处理以换行结尾的完整行：写入方只刷了半行时，`buffer.last() != '\n'` 就 `break`，下一轮再读（`:128-145`）。
- 文件变短（被重写）则 `offset` 回到 0 重读；回执保证不会重复入库（`:60-63`；测试 `:312-328`）。
- 游标 key 带版本：`CURSOR_PREFIX = "workbuddy:v2:"`；注释写明“改了哪些记录算请求时递增”，让旧文件从头重读、由回执挡住重复（`:32-35`）。

### 2.2 口径：rawUsage 到底是什么

- `prompt_tokens` 是 **OpenAI 口径，已含缓存命中**：注释明确 `prompt_cache_hit_tokens + prompt_cache_miss_tokens == prompt_tokens`；`completion_tokens` 已含思考 token（`session_usage_workbuddy.rs:1-9`；`providers/workbuddy.rs:220-224`）。
- 入库时拆成“新输入 / 缓存读 / 缓存写 / 输出”，并把 `input_token_semantics` 记为 `FRESH`（`session_usage_workbuddy.rs:7-8,95-107,162-186`）。
- 缓存读取四个字段的最大值：`prompt_cache_hit_tokens`、`cache_read_input_tokens`、`cached_tokens`、`prompt_tokens_details.cached_tokens`；缓存写取 `cache_creation_input_tokens` 与 `prompt_cache_write_tokens` 的最大值；`fresh_input = prompt_tokens - cache_read - cache_write`（饱和减）（`providers/workbuddy.rs:273-300`）。
- 没有 `rawUsage` 时退回 agents SDK 的 `providerData.usage`：只认 assistant 消息；`inputTokens` 同样含缓存，减 `inputTokensDetails[].cached_tokens`；`outputTokensDetails[].reasoning_tokens` 单列（`workbuddy.rs:302-329`）。
- 模型：`providerData.model` 优先，否则 `requestModelId`；`custom-local:<id>` / 其他 `custom-*:` 前缀去掉（`workbuddy.rs:248-255,266-272`）。
- `rawUsage.credit` 是 WorkBuddy 积分，**不是美元**，不当作费用（`session_usage_workbuddy.rs:8-9`）。上游自己用 `find_model_pricing` + `CostCalculator` 在入库时算成本（`:195-210`）；这一点我们**不该照抄**，见 §2.4。

### 2.3 失败处理

- 单个文件读/解析失败：把 `errors.push("WorkBuddy session {path}: {error}")`，其他文件继续同步（`session_usage_workbuddy.rs:64-69`）。
- 目录不存在：`files.is_empty()` 直接返回空结果，不报错（`:41-46`；测试 `:403-410`）。
- 半行：不推进游标、不报错，下一轮再读（`:132-136`）。
- 游标只有在事务里连同 `session_log_sync` 一起提交（`:190-192,358-370`）；请求插入与 `session_usage_dedup` 在同一事务，失败整批回滚。
- 汇总结构 `SessionSyncResult` 有 `imported / skipped / files_scanned / errors`，每文件独立累计（`session_usage.rs:31-54`）。

### 2.4 对照 `src/usage.js`：缺什么

结论：**`src/usage.js` 完全没支持 WorkBuddy**。`SOURCES` 只有 zcode / hermes / opencode / claude-code / codex / dsh 六个源（`src/usage.js:662-669`），没有 WorkBuddy 读取器。

若补，缺的是：

1. **源注册**：`SOURCES` 加 `{ id:'workbuddy', display:'WorkBuddy', read: readWorkbuddy }`（`src/usage.js:662-669`）。
2. **文件枚举**：复用 `src/scanners/workbuddy.js` 的 `discover()`（它同时返回顶层和 `subagents` 文件，`workbuddy.js:104-145`），按路径里的 `subagents` 段识别子代理文件，父会话 id 取上两级目录名。
3. **请求级读取**：逐行 `JSON.parse`，取 `providerData.rawUsage`（对象）或 assistant message 的 `providerData.usage`；按事件 `id` 做批内去重；一次请求只入一行。我们的 `makeRow` 已经支持 `input/output/cacheRead/cacheWrite/reasoning/semantic/model/calls`（`src/usage.js:59-87`），`normalizeFresh` 已经处理 total/fresh（`:48-57`）。
4. **口径映射**：`semantic:'total'`（因为 prompt 含缓存），`fresh = prompt - cacheRead - cacheWrite`；`output` 直接取 `completion_tokens`；`reasoning` 单列但不重复加进 output；`cost:null`、`costStatus:'unknown'`，让 `pricing.js` 在汇总层按价目表估算，**不要把今天的价格写进历史行**（这与 `src/usage.js:33-43` 的“没有价就是没有价”原则一致）。
5. **缓存**：可套用 DSH 的 `(size,mtimeMs,ctimeMs)` 缓存模式（`src/usage.js:461-487,597-604`）；但 WorkBuddy 文件是追加式，若要像上游一样记字节游标，需要额外的 `session_usage_dedup` 等价物，成本更高。建议第一版**全量重读 + 按事件 id 批内去重**，不引入持久游标。
6. **失败身份**：每文件 `{path, code, message}` 进 `reports`，不要只给 `ready:false`；我们的 `readUsage` 报告结构已支持 `reason`（`src/usage.js:682-699`）。

### 2.5 额度（`workbuddy_account/quota.rs`）— 明确不抄

### 3.2 恢复策略的三条硬纪律

1. **文件操作锁只用于“无内存状态”的锁**：`lock_file_operation` 的注释明确 “These locks contain no in-memory state; callers must still reload/validate files... Never use this for a lock protecting a database or cache.”（`sync_utils.rs:32-35`）。所以不能把“清 poison”当万能药。
2. **panic 前先回滚，回滚失败也不能吞原 panic**：`resume_after_rollback()` 在 `catch_unwind` 的 `Err` 分支里执行 rollback（rollback 自身的 panic 也只记日志），最后 `resume_unwind(payload)`（`sync_utils.rs:8-30`）。所有 DSH 多文件写、MCode/Pi prompt、pricing 文件都改用它。
3. **回滚前必须做外部修改冲突检查**：`mcode_config::write_and_commit` 先快照 `previous`，写后快照 `written`；rollback 前若 `snapshot(path) != written`，返回 `Conflict("Config changed after CC Switch wrote it; refusing to roll back ...")`，绝不把用户的外部编辑覆盖掉（`mcode_config.rs:33-97`；测试 `panicking_commit_preserves_external_edits`）。DSH 多文件写按路径排序加锁防死锁，失败时按写入逆序 `restore` 所有已写文件（`dsh_config.rs:380-460`）。

### 3.3 对照 `agent-archive`：只读场景需要什么

- **锁恢复机制整体不适用**：Node 单线程、没有 `Mutex` poison；我们也不写用户配置，没有 `<file>.lock` 需要恢复。`registry.saveCache()` 已经是 `tmp + fsync + rename` 原子写（`src/registry.js:319-359`），比上游的内存缓存更强——它跨进程可用，崩了不会留半截 JSON。
- **需要补的是“失败不被当成删除”**：见 §1.3 的 `discover()`/`statOrNull` 两处。上游的 `ScanStatus` + `complete_providers` 正是这个纪律；我们只做了“解析失败保留旧结果”，没做“发现/stat 失败保留旧结果”。
- **可借的一个只读诊断**：在 `env audit` 里扫描 DSH `profiles/*/cordis.patch.yml` 旁边的 `*.lock`：读 PID + mtime，报“有活锁（谁在写）/ stale 锁（上次写入崩溃）”。这对用户解释“为什么设置保存不了”很直接，且只读、无副作用（`dsh_config.rs:269-328`）。**值得抄（小，P3）**。
- 不建议抄 `write_and_commit` / `StagedWrite` / `ReplaceFileW` / `settings` RwLock——我们是只读，写侧复杂度是纯负担。

## §10 明确不抄清单

- **所有配置写入/锁恢复机制**：`atomic_write`/`stage_write`/`commit_staged`/`StagedWrite`/`ReplaceFileW`/`resolve_symlink_target` 的写侧、DSH `<file>.lock` 的创建与删除、settings 的 `RwLock` 写锁、`write_and_commit` 的通用文件+DB 事务、`resume_after_rollback` 本身——我们是只读，没有可回滚的用户文件。只在 §9-1 借“失败不能当删除”、§9-10 借“只读诊断”。
- **WorkBuddy 额度（WBIPC）**：`workbuddy_account/quota.rs` 的 endpoint/ticket/HMAC/`http.fetch` 全部不抄；需要 WorkBuddy 正在运行、读凭据、发请求，越过只读边界。只借 `NotRunning/NotCurrent/NotSignedIn/Failed` 四个状态词汇。
- **WorkBuddy 官方账号切换 / 登录文件还原 / `models.json` 写入**：产品功能 + 写用户配置/凭据，明确不碰（`workbuddy_config.rs:35-40` 的 official provider 只绑定账号，不写 models.json；我们也不需要）。
- **技能仓库更新 / staging 替换 / 备份轮转**：`684c388` 的 `replace_dir_staged` 是写侧修复，我们只借“隐藏 staging 不参与扫描”和“失败要可见”，不实现安装器。
- **`session_log_sync` 数据库游标 / `session_usage_dedup` 永久回执 / 入库时算成本**：我们 `usage.js` 是全量重算的只读汇总，没有账本表；引入这些会带来“空表回退重导”“历史价格固化”两类风险。WorkBuddy 用批内事件 id 去重即可。
- **`model_pricing.rs` 的本地价目表覆盖/删除 tombstone/文件+SQL 事务**：我们的 `pricing.js` 只读 models.dev 目录，成本是“估算层”，与事实层分离（`pricing.js:5-27`）。
- **`coding_plan.rs` 的套餐额度查询**：网络 + API key + 凭据；只借 URL host/路径段边界纪律（§8）。
- **`FileParseCache` / `TranscriptCache` 的 poison 恢复**：Node 没有 `Mutex` poison；已有 `transcript-cache.js` 的 LRU 等价物，且我们指纹带 ctime。无需照搬。
- **Agy 列表的“索引优先、无索引才解析转录”**：我们 `antigravity.parseAll` 已经是这个策略，**我们更强**，不重复改。
- **ToolSpec 的 npm 安装/升级命令、版本来渠道标签**：只读档案馆不安装/升级任何 CLI；只借表的组织和名字锁。
