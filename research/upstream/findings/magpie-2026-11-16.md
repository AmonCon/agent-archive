## 3. `4f40a106`：长 Claude 会话的“复制品”不再整份重读（`cc_copies.go`）

### 3.1 “copies” 在这里的语义

- Claude Code 的 `--fork-session` / `/branch` 会把整段历史复制到一个新的 session 文件；同一段历史可能出现在多个 `.jsonl` 中。magpie 把共享“首条消息 uuid 或 compaction summary uuid”的文件用 union-find 聚成一组（`cc_copies.go:52-103`），组内：
  - **copy**：一个文件的消息被另一个文件（keeper）完整持有，只补差异；`copies[fileKey] = keeperKey`（`cc_copies.go:139-183`）。
  - **branch**：组内除 head 外、还带着自己新内容的文件；`branches[fileKey] = headKey`（`cc_copies.go:184-216`）。
  - **keeper**：不是 copy 自己、且持有 copy 最后一条消息的那个文件；`before()` 先看“谁持有对方首条消息”，再看文件较新（mtime），最后按 key 排序（`cc_copies.go:139-152`）。
- `ccRest(copyFile, keeper)` 的定义：把 copy 文件读一遍，只保留 **keeper 文件里没有的消息**——包括 copy 在 compaction 之后才开始的旧段、`/rewind` 留在另一分支的消息、以及写在该文件里的子代理消息；完全不重复的 copy 得到空 state。证据：`cc_copies.go:335-397`、`399-445`；文档 `docs/subsystems/gateway-sessions.md:1298-1309`。

### 3.2 它省掉的是什么重复读取

- 旧行为：每次 `ccFamily` 判定一个组，都要从每个文件开头读 uuid；`ccRest` 每次 keeper 变化都整份重读每个 copy。对 4 个 100 MB 的 copy，`/api/sessions` 一轮 261/332 ms，优化后 26/27 ms；8 个 copy 的页面三连调用 607 ms → 31 ms（`4f40a106` 提交信息实测；设计见 `cc_copies.go:104-121`）。
- 两个增量判据（这是本轮唯一可借的“缓存判据”）：
  1. **组判定缓存**：`ccFamilyKept(sig)` 命中时，仍把组内每个文件路径标 `used`，使 `ccUUIDMemo` 保留已读 uuid；等 keeper 增长时只判新增行（`cc_copies.go:104-121`；`cc_family_memo.go` 按文件 size/mtime 存组结论，文档 `gateway-sessions.md:1298-1302`）。
  2. **copy 的 rest 缓存**：`ccRestOf` 存 copy 的 `size/mod`、keeper 的 `path/ksize/kmod`、以及 `ids`（copy 自己消息的 uuid 集合，来自 `scanThin`）；若 **copy 未变 + keeper 只增长 + keeper 不持有 copy 的任一 id**，则 `st` 原样复用，只更新 keeper 的 size/mod（`cc_copies.go:339-397`）。若 keeper 新持有了某个 id，则整段重算（测试 `TestClaudeKeeperTurnTheBranchHeldIsCountedOnce` 锁住“90 in, want 80”）。
- 读失败时**不把空当结果**：`ccRest` 的 `err != nil` 分支返回 `cache[copyFile.path]`（旧的整场 state），注释“unread is not empty: the copy is counted whole”（`cc_copies.go:389-393`）。这条和第五轮“读不到≠没有”一致。

### 3.3 与我们的 `copyOf` / `branchOf` 是否同题

| 维度 | magpie `cc_copies` | agent-archive |
|---|---|---|
| 现象 | Claude `--fork-session` / `/branch` 整段复制历史 | 同左；`src/scanners/claude-code.js:251-324` 注释明确“与 magpie cc_copies.go 同一思路，规则从简” |
| 身份判据 | 首条消息 uuid + compaction summary uuid 聚组；`holds/before` 判断 keeper | 首条消息 uuid + `summaryUuids` 并查集；`leafUuid` 相同 → `copyOf`，不同 → `branchOf`；组内按 `start` 最早选原会话，`start` 相同按路径（`claude-code.js:268-324`） |
| 用途 | **用量统计只算一次**：`ccCopyStates` 把 copy 的“rest”作为该 copy 的额外 state，`ccRest` 空的 copy 不再贡献 token；会话页统计不重复。 | **列表/搜索去重**：`copyOf` 从 `mainOnly()` 和 `buildIndex` 排除；`branchOf` 保留但标来源（`src/model.js:56-62,218-226`；`search.js:610-615`）。 |
| 我们缺的 | —— | **`src/usage.js` 的 `readClaudeCode` 按每个文件各自 `new Map()` 去重 message id**（`usage.js:305-372`，`seen` 在 `for (const file of list)` 内、`:326`）：同一 copy 的历史消息在多个文件里各有自己的 `seen`，会被多次计入。`calls.js` 只读网关日志，不读 Claude 会话文件，所以这份重复只发生在 `usage` 层。 |

**结论**：`4f40a106` 和我们的 `copyOf/branchOf` **同题不同层**——它是“内容/用量去重 + 增量读取”，我们只做了“身份/展示去重”。**可借的增量判据**是 `ccRest` 的“copy 自己的 message id 集合 + keeper 只增长且不含这些 id 时 rest 不变”；但我们的扫描缓存已经不会重读未变文件（`registry.js:646-660`），所以**性能部分我们不缺**；真正该抄的是它的**用量口径**：复制品整段为空、分叉只留自己的消息。落地建议见 §7 第 1 条。
