## 摘要（5 条）

1. **mcp-hub.md 不是被推翻，是被改名 + 扩写**：旧 `docs/subsystems/mcp-hub.md`（11.8 KB）删掉，新 `docs/subsystems/mcp-router.md`（22.2 KB）；
   同一个 `hubPool` / `/mcp/magpie/hub` 机制，改名理由是它现在**按 agent / 按 app 分发**（router），并把「服务端描述、router 名字、image 的 roots、每个调用方自己的浏览器 session」四件事加进了同一张职责表。
   **协议层可学的是失败可见性，不是转发**：工具报错必须点名服务端 + 原因，错误名不允许退化成「没开」。
2. **magpie 把「缓存失效粒度」从全局版本号改为按 agent 的版本号**（`parseVersions` / `callParseVersions`）。这是我们 `__fingerprint` 单点全量失效的直接改进方向：
   改一个扫描器不该让全部 2400+ 文件重解析。证据 `sessions.go:1110-1118`、`cache_decode.go:39-47,92`、`call_cache.go:54-60,674`。
3. **增量窗口的空闲时长从 5 分钟改成 1 小时**（`revision_cache.go:20`），理由是实测「暂停后再来一行，整份 21 MB rollout 从第一行重读」。
   这**不是**推翻我们「tail 增量否决」的结论，反而印证否决理由：他们付出窗口缓存（8 个文件 × 8192 条索引条目）的复杂度与内存，换的只是「单文件持续追加」这一场景，而代价是窗口丢失后整读。
4. **「同一趟读两用」被做实**：`callsAlong` 让摘要解析和调用解析合并成一次扫描（`call_cache.go:443-457`、`sessions.go:1974-1975`），
   实测冷启动 931 次扫描 / 3.49 GB → 718 次 / 2.10 GB。这条比缓存更值得学：**两个消费者读同一文件时先合并成一次 pass**，我们目前是 index 一遍、cat 一遍。
5. **一个真实缓存失效 bug 被修**：`callRoot` 为空时 `pruneCalls` 把「根未命名」误判为「根已移动」，把刚骑乘写入的分片全丢，下一行又整读文件（`call_cache.go:204-211`）。
   教训很通用：**「未知」不能与「已变更」共用一个判别值**——我们缓存里凡是以 `null`/空串表示「没算过」的字段都要查一遍。

#### B2 增量窗口：5 分钟 → 1 小时（复核 tail 否决）

`internal/sessions/revision_cache.go:13-20`：
> 「A Codex window lives an hour past its file's last change, as a working Claude one does. At five minutes, the turn after any longer pause read the whole rollout again from its first line, for the summary and the calls alike (#4369: a 21 MB real rollout read whole for one line) … only how long an idle one is held grew, so the most held is what one working session held already.」
上界没变：`revisionFiles = 8`、`revisionEntries = 8192`、`revisionActiveFiles = 2`（`:21-33`）。

→ **不改变我们的结论**。我们当初否决 tail 增量的实测理由是「头部哈希占热扫 0.7s，而热扫总共 2.17s」（LESSONS:130），
magpie 这次改的是**窗口存活时长**（解析中状态保留多久），不是「要不要做增量」。
它反而量出了增量的真实代价：**窗口一旦过期，就要整份重读**，所以只能靠把窗口拉长到 1 小时（并用 8 窗口上限兜内存）。
我们的方案是「ctime 判据 + 整读」，没有窗口过期问题，也没有 21 MB 重读问题。**维持否决**。

#### B3 同一次 pass 服务两个消费者（`callsAlong`）

- 位置：`call_cache.go:443-457`（`callsAlong(f, sum)` 现覆盖 codex 与 claude/claude-desktop）、`sessions.go:1974-1975`
  （`if calls != nil && (s.Off != 0 || calls.st.Off != 0) { calls.release() // a read goes on from where it was`）。
- 实测（提交 `2140f5b`）：「copies of the owner's real ~/.codex and ~/.claude (1.7 GB), a cold start scanned 931 times, 3.49 GB, every large rollout x2」→ 718 次 / 2.10 GB。
- 顺带修的失效 bug：`call_cache.go:204-211`：
  > 「what is kept is of this root: a Sessions parse that read a rollout's calls along (callsRide) keeps them before any Requests read named the root, and pruneCalls then took the root for a moved one and dropped them, Codex window and all.」
- 一个不留死角的细节：`call_cache.go:456` 用 `os.Stat(callCachePath(f.path))` 判「这个 claude 会话的调用分片是否已存在」，
  而不是只看内存 map——因为分片可能在盘上而内存里没有。

→ **建议采纳（形态）**：我们 `index`（搜索/时间线）与 `cat`/`web`（正文）现在是两趟读同一文件。
若某文件本轮已整读，把它「已解析的正文」顺手进 `transcript-cache.js`，可省一次整解压（Codex `.zst` 实测 1.1s/次）。

#### B4 读放大与「目录/字符串」两件事分开了（复核目录缓存否决）

- `one_listing.go`（**旧文件，本轮未改**）：`heldFiles(key, list)` 在**一次请求内**共享同一目录列举，`gen` 用**计数器不用时间**——
  `one_listing.go:16-20`：「A count, not a time: on Windows two `time.Now()` a moment apart can be the same, and a hold begun in the tick a listing was taken in counted that older listing as its own (#4114)」。
- 本轮新东西是**字符串复用**，不是目录缓存：`sessions.go:597-637` 的 `ccListed`/`ccNames.of`/`joinedIs`，
  按上一次列举的 path/key 逐位比对复用，容忍「一个新文件或消失一个」（`sessions.go:616-624` 只往前探 2 位）。
  量级：`sessions.go:597-602`：「making each file's path and key again was ~10 MB of every poll over ~15k sessions」。

→ **维持「目录列举缓存否决」**：magpie 的收益来自「15 秒轮询 × 万级会话」的场景，我们的扫描是 5 分钟 TTL + 10 分钟页面缓存，
且成本在逐文件 stat/解析而不在 readdir。**但记下这条方法论**：跨平台「用计数器不用时钟」做代际——我们在 `platform.js` 里若做类似守卫，同样要防 Windows 时钟精度（magpie 为此被咬过一次 #4114）。

## 建议采纳（按性价比排序）

1. **per-scanner 缓存指纹**（B1）。把 `registry.js` 的单一 `__fingerprint` 拆成按扫描器；缓存条目加 `scanner` 字段，指纹不符只丢该家的条目。
   收益：改一个扫描器时不再重解析全部 2400+ 文件。成本：小（改 `scannerFingerprint()` 返回形状 + 一处过滤）。**这是我们目前最贵的一次全量重扫的根因。**
2. **「未知 ≠ 空/已变更」的判别值分离**（摘要 5、B3 的 bug）。检查我们缓存/索引里所有以 `null`、`''`、`0` 同时表示「没算过」和「算过但确实为空」的字段，
   逐个拆开。magpie 为这个 bug 付了「合并写入的分片整片被 prune 掉」的代价。
3. **一趟读两用**（B3）：index 与 cat 共用一次解析。优先级低于 1、2（我们已有 `transcript-cache.js` 挡第二趟），但 Codex `.zst` 场景收益明确。
4. **错误答复纪律**（A1/A2）：我们 `doctor`/`mcp.read_session` 的失败答复里，
   「这个 Agent 我不支持读」与「我这次读失败 / 文件不见了」当前是否同形？按 magpie 的写法应是两句不同的话，且失败那句要带原因与位置。

## 不采纳

- **mcp router 的转发/进程池/session 分发/roots 协商**（`mcp-router.md:18-19`）：我们不转发请求、不起子进程、不写用户配置。
- **`Server.Hub = direct` 的 per-server 策略、router 名字、`initialize` 描述预算（250/2000 字符）**：全部服务「给模型看的提示词」，我们不注入。
- **账户权重 / 额度窗口 / rate window 计价 / checkin**（`account_weight.go`、`ratewindow.go`、`provider/checkin.go` 等）：产品功能（计费与账户管理），且我们不转发请求。
- **Codex rollout 的原地改写**（`codex_portable.go` 全篇：`magpie_reasoning`、`retireReasoning`、`repairLineages`、`portLine`）：
  这是**写**会话文件以修 OpenAI 侧兼容性，我们是只读档案馆；`content.go:357` 加 `magpie_reasoning` 分支也只是跟随它自己的写方。
- **`setupCalls`/`hubSandbox` 式的进程母树、LAN key 守卫**：不存在于我们的架构。
- **`list_kept.go` 的整列表缓存（1 分钟 TTL + 逐字段验证，`list_kept.go:13,37,43-53`）**：其存在前提是「15 秒轮询 + 34k 会话 + 页面每轮全量重排」；
  我们已有 10 分钟扫描缓存（`registry.js:627`）与页级缓存，重排成本不构成瓶颈。**但它的验证函数形状可借**：
  `stats_kept.go:69-79` `keptStill(...)` 把「文件没变 **且** 价格/标题/Desktop 名这些**派生输入**也没变」一起作为命中条件——
  提醒我们：缓存命中判据若含派生查询（价格表、别名表），那些输入也必须进判据，否则会出现「文件没变但标题变了、页面还是旧的」。
