### A1. per-scanner 缓存指纹：改哪家只付哪家的钱

**现状（核过）**

- [`src/registry.js:104`](../../../src/registry.js) `CACHE_VERSION = 5`；`:107` `FINGERPRINT_KEY = '__fingerprint'`（单键）。
- `:138-153` `scannerFingerprint()` / `computeScannerFingerprint()`：**把所有内置 + 用户扫描器逐个 SHA-256 后拼进同一个哈希**，返回一个 12 位十六进制串。
- `:391` `const cache = loaded && loaded[FINGERPRINT_KEY] === fingerprint ? loaded : {};` —— 一个值不等，**整份缓存作废**。
- `:481` `nextCache[key] = { stamp: stampToStore, sessions: normalized };` —— 条目里**没有** `scanner` 字段，所以事后无法「只丢某一家的条目」。
- `:493` `nextCache[FINGERPRINT_KEY] = fingerprint;`

**代价 [实测]**

| 场景 | 耗时 |
|---|---|
| 热扫（缓存全命中） | 1021–1248 ms |
| 全量重扫 `noCache` | 37.1–65.9 s（两次运行差异来自 SQLite 临时副本冷热） |
| 逐家 `noCache, only:[x]` | codex 15245 ms / 2039 文件；**qoder 25876 ms / 447 文件**；dsh 2679 ms / 71 文件；其余每家 < 300 ms |

**收益不是线性的，是「改哪家只付哪家」**：改 `claude-code.js` 一个字符，今天付 35.8 s，改完付约 39 ms（它只有 2 个文件）。900 倍量级差。改 `codex.js` 仍要付 15.2 s——这是该方案的天花板，不是缺陷。

**改法（四处，都在 registry.js）**

1. `:143-153` 改成返回映射，不再折叠成一个值：

   ```js
   // 返回 { 'claude-code': 'ab12…', 'codex': 'cd34…', 'user:my-scanner': 'ef56…' }
   function computeScannerFingerprints() {
     const out = {};
     for (const [rel, full] of listScannerSources(builtinDir, false)) {
       out[builtinNameOf(rel)] = fileHash(full).slice(0, 12);
     }
     for (const [rel, full] of listScannerSources(statePath('scanners'), true)) {
       out[`user:${rel}`] = fileHash(full).slice(0, 12);
     }
     return out;
   }
   ```

   注意：`builtin:` 前缀现在只用于「内置删一个、用户加一个不互相抵消」，改成按名分键后**天然不抵消**，前缀可去掉；但 `user:` 要留（用户扫描器可能重名）。

2. `:391` 的判定拆成两步：

   ```js
   const fingerprints = scannerFingerprints();
   const prevFp = loaded && loaded[FINGERPRINT_KEY];       // 老格式：一个字符串
   const perScanner = loaded && loaded.__fingerprints;     // 新格式：一个映射
   // 老缓存（没有 __fingerprints）一律保留条目、只补名 —— 见下面的迁移规则
   const cache = loaded && (perScanner || prevFp) ? loaded : {};
   ```

3. `:414-441` 循环里把「是否允许命中」提前算出来：

   ```js
   const prev = cache[key];
   const fpOk = !prev || !prev.scanner || !perScanner
     || perScanner[prev.scanner] === fingerprints[prev.scanner];
   if (prev && fpOk && sameStatOnly(prev.stamp, statStamp)) { /* 原来的第二层 */ }
   ```

4. `:481` 条目带上归属，`:493` 写新键：

   ```js
   nextCache[key] = { scanner: scanner.name, stamp: stampToStore, sessions: normalized };
   nextCache.__fingerprints = fingerprints;
   ```

**迁移规则（照 magpie，别丢条目）**

magpie 的 `cache_decode.go:39-47` 专门处理「老缓存条目没有 agent 名」：**只有当没有任何 agent 的版本动过时才保留**，`:92` 才逐条按 `p.Agent != "" && was[p.Agent] != parseVersions[p.Agent]` 丢弃；`sessions.go:1332-1338` 更进一步——第一次刷新时**顺手补名而不是丢弃**。

对我们：首次运行发现 `loaded.__fingerprints` 不存在时，**一个条目都不要丢**，只给每条补 `scanner` 名并写下新键。否则升级本身会触发一次 35.8 s 全量重扫，用户体感是「更新完第一屏卡了 40 秒」。第二次运行起才按家作废。

**风险**

- `nextCache[key].scanner` 用 `scanner.name`，而 `discover()` 里同一文件理论上可能被两家发现（实测 0 例）。若发生，后一家会覆盖前一家的 `scanner` 标记 → 前一家改代码时不会作废这一条。可接受（下次 stat 变化就修正），但值得在代码里留一行注释。
- 用户删掉一个用户扫描器：它的条目再也不会被 `discover()` 产出，`nextCache` 里自然消失；但 `only` 分支（`:400` `{ ...cache }`）会保留其他家条目，这些孤儿条目会一直留着。今天的行为也一样（整份作废），**不构成回归**。

**验证**

- 改 [`test/registry.test.js:154`](../../../test/registry.test.js) 那条：现在只断言「指纹变了就全量重扫」。新增一条：两个 agent 各造一个文件，把 `__fingerprints` 里**只有 dsh 的**值改掉 → 断言 `stats.parsed === dsh 的文件数`，另一家 `stats.cached > 0`。
- 保留原用例（全局不一致时仍然全量重扫）——那是 `__fingerprints` 整个缺失时的退化路径。
- 度量：改 `src/scanners/dsh.js` 加一个空行，跑 `scanAll({})`，`stats.parsed` 应从 2579 降到 71，耗时 35.8 s → 约 2.7 s。

**上游证据**：magpie `sessions.go:1110-1118`（`parseVersions`，注释原话「a raise of `cacheVersion` reads every file of every agent again, minutes of CPU for a long history after each update (#2278)」）、`cache_decode.go:39-47,92`、`call_cache.go:54-60,674`；cc-switch `session_usage_pi.rs:37-43,176-186`（标记换代，只重扫受影响 flavor，靠持久账本消重）。

### A2. DSH 候选根大小写别名 → 整家正文读不出来（**真 bug，已复现**）

这一条两份 findings 都写成了「潜在缺陷、未证实、可能只是重复解析」。**复核后性质变了**：后果不是「重复拼接」，是**硬失败**。

**现状（核过）**

- [`src/scanners/dsh.js:70`](../../../src/scanners/dsh.js) `if (isDir(path.join(r, 'sessions')) && !out.includes(r)) out.push(r);` —— 裸字符串比较，`roots` 直接来自 `extraRoots(name)` / `envOverrides(['DSH_HOME'])` / `path.join(home, …)`，**没有 `path.resolve`、没有大小写归一**。
- `:163-191` `discover()` **没有去重**：`for (const root of dshDirs())` 直接 push，同一个 session 目录经两个根各产出一次。
- [`src/registry.js:658`](../../../src/registry.js) `if (s.source && !prev.sources.includes(s.source)) prev.sources.push(s.source);` —— 又一次字符串比较，两种拼写都进 `sources`，最终 `:664` 用 `'|'` 拼起来。
- [`src/scanners/dsh.js:263-268`](../../../src/scanners/dsh.js) `readMessages`：`const file = assertUnderAny(roots, session.source); const lines = readLines(file);` —— **不拆 `'|'`**，把整串当成一个路径交给 `readFileSync`。

**复现 [实测]**

```
$env:DSH_HOME="<同一个目录的全小写写法>"   # 复现命令里的真实路径已换成占位符
candidateRoots() → 2 条（大小写不同，同一目录）
discover()       → 142 个文件（基线 71，正好 ×2）
mergeByKey 后      → 71 场会话，但 source 有 2 段
readSessionContent → Error: ENOENT … 'c:\…\deepseekharness\sessions\…\session.v4.jsonl.zstd|C:\Users\…\DeepSeekHarness\sessions\…\session.v4.jsonl.zstd'
```

也就是说：**任何把 `DSH_HOME`（或 `config.js` 的 `roots.dsh`）写成大小写变体的用户，DSH 整家的 `cat` / 网页会话页 / MCP `read_session` 全部报 ENOENT，而 `timeline` / 索引看起来完全正常**。这是最难查的一类：列表对、正文挂。

**改法（三处，第三处才是根治）**

1. `dsh.js:68-72` 用 [`src/platform.js:87`](../../../src/platform.js) 的 `pathKey`（已导出，`samePathNorm` 在 `:93-94` 就是它）：

   ```js
   const out = [];
   const seen = new Set();
   for (const r of roots) {
     if (!isDir(path.join(r, 'sessions'))) continue;
     const k = pathKey(r);
     if (seen.has(k)) continue;
     seen.add(k); out.push(r);
   }
   ```

2. `dsh.js:163-191` `discover()` 加文件级去重，**照 [`src/scanners/qoder.js:114-121`](../../../src/scanners/qoder.js) 的写法抄**（那里已经用 `pathKey(file)` 做对了）：

   ```js
   const seen = new Set();
   const add = (f) => { const k = pathKey(f); if (seen.has(k)) return; seen.add(k); out.push(f); };
   ```

3. `registry.js:658` 改成按 `pathKey` 去重。这一处是**兜底**：任何扫描器（含用户写的）都不会把同一文件记两次。1 行改动，保护全部 11 家。

**为什么不用 cc-switch 的 `realpath(父目录)+文件名`**

cc-switch 要 realpath 是因为它**要写**：同一把 `<file>.lock` 取两次会让每次写都报假冲突（`dsh_config.rs:39-43`）。我们只读，realpath 的额外收益只有「junction / 8.3 短名」，而代价是每个候选根一次真实 IO，且 `fs.realpathSync.native` 对「文件还不存在」的路径直接抛错（cc-switch 的注释里专门解释了它为什么选父目录：`dsh_config.rs:62-67`「The file itself may not exist yet … but its parent always does」）。

`pathKey` 是纯字符串归一（大小写 + 分隔符），零 IO，且**我们已经有它、已经有三家在用**。见下面「我不同意上游的地方」第 1 条。

**验证**

- 新增用例（`test/dsh.test.js`）：`sandbox()` 里造一份 DSH 数据，`process.env.DSH_HOME` 设成全小写形式 → 断言 ① `discover().length` 等于基线，② `scanAll({only:['dsh']})` 里任一会话 `source` 不含 `'|'`，③ `readSessionContent(s)` 不抛错。
- 这条用例**共享 fixture 替代不了**：它是「同一份数据 + 不同环境输入」，不是「不同数据」。

**上游证据**：cc-switch `dsh_config.rs:39-43`（`#9100`，原话「Listing both spellings made `edit_files_and_commit` take the same `<file>.lock` twice, so every provider and MCP write failed with a bogus concurrency conflict」）、`:62-76`。

**顺带核到的对照（结论与 findings 的写法不同）**：findings 把 `dsh.js:70` 与 `qoder.js:81` 并列。实际上 `qoder.js` 的**根级**去重（`:81`、`:91`）虽然是字符串比较，但它的 `discover()` 用 `pathKey` 做了文件级去重（`:114-121`），所以根重复只是多几次 `readdir`，**没有正确性问题**；`codex.js:64-79` 的 `codexDirs()` 也用了 `sameNorm`。**只有 dsh 两处都缺**。这是「同一纪律落地程度不一」的典型，不是「我们整体都缺」。

### A3. codex 旁路库 memo：判据缺 `-wal`，且把「读失败」当成「读到了空」

这一条**两份 findings 都没覆盖到我们这一处**——属于第三类问题，见第四节 C-3 的归纳。

**现状（核过）**

[`src/scanners/codex.js:654-699`](../../../src/scanners/codex.js) `threadIndex()`：

- `:657-663` 判据是 `stamp = \`${st.size}:${st.mtimeMs}\``，**只看主库** `state_5.sqlite`。
- `:664` `if (threadIndexMemo && threadIndexMemo.stamp === stamp) return threadIndexMemo.map;`
- `:686-687` `catch { /* 表结构变了或读不了：当空表处理 */ }`
- `:697` `threadIndexMemo = { stamp, map };` —— **无论 `openReadOnly` 返回 null 还是 `prepare` 抛错，都会把这次结果写进 memo**。

**两个独立缺陷**

1. **判据漏了 WAL**。实测 `~/.codex/state_5.sqlite` 头部第 18/19 字节都是 `2` [实测] → **WAL 模式**，同目录有 `state_5.sqlite-wal` / `-shm`。WAL 模式下的写入先落 `-wal`，**主库的 size/mtime 只在 checkpoint 时才变**。所以「Codex 刚给一场会话改了标题」这段时间里，`stamp` 不变 → memo 命中 → `enrich` 一直用旧标题，直到某次 checkpoint。长驻的 `serve` 进程里这个窗口可以很长。
   我们已经为**扫描层**学过这一课（[`LESSONS.md:24`](../LESSONS.md) 的 `extraFiles()` + `stampOf()`，`registry.js:280` 的 `sizeOnly`）；**旁路层没有复用同一套判据**。
2. **「未知」被当成「空」**。`openReadOnly` 返回 null（临时打不开、被替换、权限抖动）或 `prepare` 抛错时，`map` 是空 Map，而 `:697` 照常 memo 化。`enrich`（`:735`）看到 `index.size === 0` 就 `return sessions`——看起来完全正常，只是「end 精度变粗、标题变占位」，**不报错、不进 `stats.enrichErrors`**（`enrich` 没抛错，[`registry.js:565-569`](../../../src/registry.js) 捕不到）。这正是 magpie 那个 bug 的形状：`callRoot` 为空被当成「根已移动」，把刚写好的分片全 prune 掉（`call_cache.go:204-211`）。magpie 的教训原话：**「未知」不能与「已变更」共用一个判别值**。

**改法**

1. `sqlite-read.js:97-128` 的 `copyFor` 里已经有一份**正确**的判据：`:98` `stamp = \`${dbStat.size}:${dbStat.mtimeMs}:${walStat ? \`${walStat.size}:${walStat.mtimeMs}\` : 'nowal'}\``。把它提成一个导出的 `stampForDb(file)`，`copyFor` 与 `codex.threadIndex` **共用同一个函数**——不要让第三份判据出现。
2. `codex.js:660` 改用 `stampForDb(dbPath)`。
3. `codex.js:686-697`：读失败时 `return null`，**不写 memo**。`enrich`（`:735`）已有 `!index → return sessions` 的兜底，所以行为不变，只是下一轮会重试。
4. **`enrich` 的「只填不清」已经满足，不用改**（这条我同意 lead 的核对）：`:748` `if (t.updatedAt && (!s.end || t.updatedAt > s.end))` 只在更晚时替换；`:755-757` 只在 `theirs` 非空且我们是占位标题时替换。cc-switch 建议 1 的**前半**（只填不清）对我们是「已满足」。
5. 真正缺的是建议 1 的**后半**：跨文件取真值后复验「取的时候它没被改」。用 `stampForDb` 在 `:667` 读之前、`:697` 之后各算一次，不等就丢弃本次结果、下轮重试（照 cc-switch `session_usage_codex.rs:2050` 捕获 + `:2096-2098` 复验）。

**风险**

- 复验会让「库一直在被写」的机器上偶发不命中 → 每次扫描多读一次 48 ms。可以接受（48 ms vs 15.2 s 的 codex 重解析）。
- `stampForDb` 提到 `sqlite-read.js` 会让 codex.js 多一个 import。可接受，那个文件本来就是「怎么安全读 SQLite」的唯一出口。

**验证**

- 新用例（`test/codex.test.js`）：`sandbox()` 造一个小 `state_5.sqlite`（WAL 模式），写入一行 title 后**不 checkpoint**，跑一次 `scanAll`；再写第二行 title（仍不 checkpoint），再跑一次，断言第二次的 `title` 是新值。今天这条会失败。
- 用例 2：让 `threadIndex` 内部抛错（用一个缺列的表模拟），断言 `enrich` 返回原数组，**且第二次调用会重试**（memo 未被污染）——可以用 `enrichStats().indexed` 断言为 0 而不是 `>0`。
- 度量：`enrichStats()`（`codex.js:782-784`）在修复后应能区分「0 条」与「没读到」。

**上游证据**：cc-switch `session_usage_codex.rs:2050`（`ParentFileStamp::from_file`）、`:2096-2098`（读完复验）、`:1923-1957`（`MissingParent / Stable / Retryable` 三态，只在 reason 变化时 `log::warn`）；magpie `stats_kept.go:69-79` `keptStill(...)`（把价格/标题这些**派生输入**也作为命中条件）、`call_cache.go:204-211`（未知 ≠ 已变更）。

### A4. 失败答复三态：「我不认识」「读不出来」「确实没有」

**现状（核过）**

- [`src/mcp.js:193`](../../../src/mcp.js) `if (!matches.length) return { error: \`没有匹配 ${id} 的会话\` };` —— 一句话覆盖了三种完全不同的情况：

  3. 确实没有这场会话（**它不存在**）。

- `registry.js:688-698` `parseFile` 的 `catch { return { sessions: [], ok: false }; }` —— **异常对象被直接丢掉**，连 `e.message` 都没留。
- 已经做对的部分（这点比 cc-switch 强，值得记进台账）：`registry.js:457` 把 `!ok`（抛错）与 `emptied`（曾有好结果、这次空）分开，且两者都保留上一次的好结果（`:458-467`）——cc-switch 的 `join().unwrap_or_default()`（`session_manager/mod.rs:72-80`）是把 panic 变成空列表，我们不是。

**改法（最小可执行版）**

2. `registry.js:402` 加 `problems: []`；`:458-467` 在 `!ok` / `emptied` 分支里 push `{ agent: scanner.name, file, kind: 'parse'|'emptied', reason }`，**上限 50 条**（缓存文件是 JSON，无上限会膨胀；今天缓存已 1 MB 量级）。
3. `mcp.js:191-193` 拆三句，且每句都带下一步：

   ```js
   const known = scanners.map((s) => s.name);
   if (agent && !known.includes(agent)) {
     return { error: `我不认识 Agent「${agent}」`, knownAgents: known };
   }
   if (!matches.length) {
     const p = problemsFor(id);        // 从 scanCached().stats.problems 里找
     if (p) return { error: `会话存在但这次读不出来：${p.reason}`, file: tildify(p.file), kind: p.kind };

   }
   ```

### C1. 「一趟读两用」（magpie 的 `callsAlong`）—— 我们已经做到了，不需要新工作

magpie 的 `callsAlong`（`call_cache.go:443-457`）让摘要解析和调用解析合并成一次扫描，冷启动 931 次 / 3.49 GB → 718 次 / 2.10 GB。听起来正对「我们 index 一遍、cat 一遍」。

### C2. ContentRef 式正文指针（LESSONS 待办 #4）—— **建议从待办里删掉，改成「已否决」**

LESSONS 现在写的是「pending（边际收益重估）」，理由是「压缩已经拿掉 26% 体积，指针化的边际收益需要重新评估」。**本轮拿到的是决定性理由，不是边际理由。**

### C-3.1 「派生输入也要进缓存命中判据」——我们做对了一处，漏了一处

magpie 的 `stats_kept.go:69-79` `keptStill(...)` 把「文件没变 **且** 价格/标题/Desktop 名这些**派生输入**也没变」一起作为缓存命中条件。两份 findings 都把它当成「list_kept 的附带细节」，但它其实是一个**横切的纪律**，而我们三条缓存路径的落地程度完全不同：

|---|---|---|---|
| `codex.js:686-697` `threadIndexMemo` | 读失败 → 空 Map，且**被 memo 化** | 表真的没有行 → 空 Map | 进程生命周期内不再重试，标题/end 静默变粗（A3） |
| `registry.js:457-467` | `!ok`（抛错）→ 保留旧值、沿用旧指纹 | `emptied`（曾经有、这次空）→ 同上 | **已分开**，且都保留旧值——比 cc-switch 强，不用改 |
| `mcp.js:193` | 「我不认识这个 Agent」/「文件在但读不出来」 | 「确实没有这场会话」 | 三种情况同一句话（A4） |

**判据**：凡是同时用 `null` / `''` / `0` / 空 Map 表示「没算过」和「算过但确实为空」的字段，都要拆开。本轮查完，只有 `codex.js:697` 一处是**真缺陷**。

### C-3.3 我们独有的欠账：失败只有计数，没有身份

两份 findings 分别从不同方向指到同一件事——magpie 要求错误**点名服务端与原因**（`mcp-router.md:32`），cc-switch 要求**汇总所有源的失败再上抛**（`exchange_rates.rs:132-135`）——但都没说到我们真正的形状：

**我们的失败在采集完就丢失了身份。** `registry.js:402` 的 `stats` 里 `failures` / `emptied` / `keptStale` 是纯计数，`parseFile`（`:688-698`）连异常 message 都扔了。于是：

- `doctor` 只能说「3 个失败」，说不出**是哪个文件、为什么**（`doctor.js:139`）；
- MCP 的 `read_session` 无法把「这场读不出来」和「没有这场」分开（A4）；
- 缓存里的 `keptStale` 会话（保留了过期内容的那些）**没有任何出口**能让用户知道「你看到的可能是旧的」。

这条是「失败可见性」在我们架构里的最小落地，成本极低（A4 的 1+2 两步），收益是把 doctor 从「计数器」变成「诊断工具」。

顺带记一条与本轮无关但同类：LESSONS:156-157 记的「子代理断链只在 doctor 可见，query/MCP/Web 没有 orphan 出口」是同一个病的另一个症状——**事实被算出来了，但没有出口**。这两条可以一起做。

### C-3.4 「同一纪律落地程度不一」的第二个实例：候选根去重

A2 里已经写了：`codex.js:64-79` 用 `sameNorm`、`qoder.js:114-121` 用 `pathKey`、`platform.js:56,73` 用 `samePathNorm` —— **三处各自实现了一遍「路径归一」**，而 `dsh.js:70,163-191` 一处都没用。

`platform.js:93-94` 的 `samePathNorm` 就是 `pathKey(a) === pathKey(b)`，`pathKey` 已经导出（`:87`）。所以这不是缺能力，是**缺一次「把归一统一到一处」的清扫**。

**可执行的检查**：`grep -n "includes(" src/scanners/*.js` —— 所有对**路径**用 `includes` / `Set` 做身份判断的地方都要过一遍。（本轮已过完：真缺陷只有 dsh 两处。）

### C-3.5 测试夹具的反面：环境输入型 bug 需要另一类用例

LESSONS 待办 #1（共享 fixture）隐含的假设是「把漂移样本抽成 JSON 就够了」。A2 证明**不够**：那个 bug 的数据是完全正常的 DSH 会话文件，坏的是**环境输入**（`DSH_HOME` 的大小写）。

所以我们缺的不是一类夹具，是**两类**：

- **数据夹具**（fixture）：同一份字节，多入口共用 → B2；
- **环境夹具**：同一份数据 + 不同的 `DSH_HOME` / `CODEX_HOME` / `roots.*` / 大小写 / 分隔符 → 这类用例**必须能改环境变量**。

`test/helpers.js` 的 `sandbox()` 已经能改根目录，但 A2 的用例要能设 `process.env.DSH_HOME`，需要确认 sandbox 会把 env 也隔离（`box.run(() => …)` 里设 `process.env` 再恢复）。这是 B2 实施时的第一个待办。

## 六、我不同意上游做法的地方

1. **路径身份不要照抄 realpath**。cc-switch 用 `realpath(父目录)+文件名`（`dsh_config.rs:68-76`）是因为它**要写**、要避免同一把 `.lock` 取两次；它的注释也解释了自己为什么选父目录而不是文件本身（「文件可能还不存在，父目录总在」）。我们只读，realpath 的增量收益只有 junction / 8.3 短名，代价是每个候选根一次真实 IO，且对不存在的路径会抛错。**`pathKey`（大小写 + 分隔符归一，零 IO，我们已经有三处在用）足够，照抄 realpath 是引入我们不需要的约束。**

2. **`callsAlong` 的形态不适用，别按它重构**。它是「同一个常驻进程里两个消费者共用一次 pass」。我们的 `index` 与 `cat` 是两个 CLI 进程，而且 `index` 本来就是一趟读两用（`search.js:620-623`）。照抄会逼我们引入常驻进程或落盘正文缓存——前者是我们明确不做的（不写用户文件、不做多租户常驻），后者是 C2 已否决的方向。

3. **ContentRef 的成立前提我们不具备，不要把「未评估」当成「值得做」**。cc-switch 的 `ContentRef` 读明文 `.jsonl`，能按 offset 定位；我们主力是 zstd 单帧，物理上做不到。把这条一直挂在 pending 会让每轮深读都重新评估一遍——**「明确的否决」比「待评估」更省**。

4. **magpie 的 tail 增量对我们不是「还没做」，是「不该做」**。它自己为增量付的税（窗口过期整份重读、8 个窗口 × 8192 条索引条目的内存）在它的场景里值得，因为它是**5–15 秒轮询的常驻网关**。我们是**按需扫描 + 5 分钟 TTL**，没有那个轮询频率，也就没有那笔收益。

5. **cc-switch 的「MCP 连通性探测只给红/绿、不记录传输错误」我们**不能**学**（`mcp_connectivity.rs:101-104`）。它选最保守那一档是因为它的定位不需要诊断，**我们需要**——我们是诊断工具，doctor 的价值就在「说出为什么」。正确做法是**脱敏后再可见**（错误文本里可能有用户路径、env 值），不是二选一。

6. **`codex.js:374` 那条待复核是假警报，不要顺着上游改**。magpie 的 `tsAt(b, last)` 是它**自己字节层解析**的补丁；我们走 `JSON.parse`（`codex.js:377-379`），内嵌 timestamp 不会被选中。顺着「取最后一个」改，会让 `indexOf` 预筛与 `JSON.parse` 的语义脱钩，反而制造不一致。
